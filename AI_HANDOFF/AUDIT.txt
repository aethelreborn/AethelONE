## Session 2026-10-11 (cont) — animation + texture + first-person visibility
5. Pet polish — commits 51a63ce1 (aethelone/main) + 8fb2014 (aetheloneplus/main).
   User reported 3 defects on the follow pet: (a) totally static (no animation),
   (b) very low quality, (c) not visible in first person (only F5/freelook).
   Root causes found & fixed:
   (a) No animations were shipped. The FBX has 8 anims (move, Stand, Sleep, etc.)
       but on a Bip002 humanoid rig whose bone names/rest-pose don't match my
       box-skeleton bones (wing_L, tail1-3, torso...). Raw-porting FBX keys would
       need a full bone remap; instead authored Bedrock animations directly:
       * baby_deathripper.animation.json in BOTH bundles:
           animation.babydragon.move (0.5s loop): big mirrored wing flap (Z ±42°
             on wing_L/R, tips lag ±18°), tail sway, slight torso pitch, neck bob.
           animation.babydragon.idle (2.0s loop): gentle wing flutter (Z ±10°),
             tail sway, subtle neck/skull motion.
       * pet.json gains "states":{"idle":<idle anim>,"move":<move anim>} (both bundles).
         PetEntity.animationState flips idle→move when distance > 0.3 ticks; the
         Bedrock controller runner blends between them (ANIMATION_BLEND_TICKS).
       Verified: anim JSON parses, stateMap names resolve, every animated bone
       exists in the geometry (missing-bones=[]), timestamps are numeric seconds.
   (b) Texture had been downscaled 1024→256 in v1. Restored the ORIGINAL 1024x1024
       PNG (from ~/Documents/baby-deathripper.zip) into both bundles. Geometry
       texture_width/height bumped 256→1024 and ALL uv / uv_size coords scaled x4
       (UVs are normalized by the declared texture dims in BedrockMesh, so scaling
       both keeps the mapping identical at full res).
       NOTE: detectFrameCount(png, declaredHeight) — if the PNG is a multiple of
       the declared height it's treated as a flipbook. Declared height now MATCHES
       the PNG (1024), so frameCount=1 (no accidental flipbook).
   (c) First-person cull: PetEntityRenderer.shouldRender had 3 version-gated copies
       that returned false when cameraType.isFirstPerson (or perspective==0 on
       1.8.9) && isOwnPet — hiding your OWN pet in first person. Removed all 3.
       Also the flying pet hovered 90° to the LEFT (pure leftVector*1.3), i.e.
       outside the forward FOV. Now hovers ahead-and-left: left*1.1 + forward*0.9
       at y≈1.55 (head height), so it sits in the first-person view. Both the
       26.3 (Vec3) and 1.8.9 (DoubleArray) desiredPosition paths updated. Added
       forwardVector(ownerYRot)=(-sin,0,cos) alongside the existing leftVector.
   - Proxy hashes are runtime-computed (LazyLock sha1 of include_bytes!) →
     swapping the asset zips auto-updates the served hashes, no Rust edits needed.
   - CI: launcher nightly 38108023353 GREEN (incl. test job, proxy tests still pass
     since only asset bytes changed); mod build 38108086808 all 10 MC versions GREEN.
   - Fresh artifacts in /mnt/antix/home/darkie/Downloads/ (verified file types):

   instead of generic internet advice; the hint only arms when the API URL is
   loopback, so production backends keep yesterday's text. While gating the
   release the new workspace test step caught a date bomb from the servers
   page (8bc6c863): its ordering test stamped a join at a fixed
   2026-10-18T12:00:00Z literal that string-compares below every fresh
   created_at from the next UTC day on, so the suite could never pass again -
   the stamp is now derived from now + 365d (6617b5a1). 2.29.1: nightly green
   (second attempt, after that db fix), 18 assets, latest.json, deb verified
   23.0 MB.

   LESSON: a launcher that owns a local service another process depends on
   must not exit while that process is alive - once a game is running, window
   close and application quit are different verbs. And never bake a fixed date
   into one side of an ordering test when the other side comes from sqlite's
   CURRENT_TIMESTAMP: derive every key from the same clock, or the test is a
   bomb set to detonate at the next date boundary, exactly like this one.

## 2026-10-21 - Performance Mode ships in 2.30.0 (iteration 14)
   Iteration 14: the launcher promised performance and delivered a promise, so
   it now does the work. Settings - Minecraft carries a Performance Mode row
   (Off, Balanced, Low-spec) that names the machine ("3 GB of memory, 2
   cores"), says which mode fits it and lists every change the mode makes. At
   launch the plan is applied: the collector is told how long it may hold a
   frame (-XX:MaxGCPauseMillis=50), the repeated strings the game holds are
   stored once (-XX:+UseStringDeduplication, only with the collector that
   supports it), the low-spec mode hands the game a heap the machine can
   afford so a 4 GB laptop stops paging, and the video settings the mode
   promises are written into the game's own options.txt before every launch
   (render distance, simulation distance, particles, entity distance, clouds,
   and on the low-spec mode fast graphics, no ambient occlusion and a smaller
   mipmap). Instances that carry mods keep the memory they need: a pack that
   needs four gigabytes is never handed less. New: the oneclient_common
   performance module (PerformanceMode, SystemProfile, the plan), the mode in
   the profile's os_extra (a JSON column, so no migration was needed), the
   options writer in the cluster crate and the launch wiring in the core.
   Committed e7ee5d4d + 2fa94c69; nightly green; release 2.30.0, 18 assets.

   LESSON: a launcher that claims to raise the frame rate has two levers - the
   garbage collector and the game's own video settings - and everything else
   is a promise. The third lever is the memory: on a 4 GB machine the stutter
   is usually the system paging, not the game, so the heap the game is given
   matters more than any flag. And a machine that cannot link cannot verify
   anything: this box has no MSVC toolchain, so cargo cannot build a single
   proc macro and the CI is the only compile gate - keep the commits small
   enough that a red run names the change that broke it.

## 2026-10-21 - The upstream merge lands (2.32.0) and the sync stops failing
   The Upstream Sync workflow had been failing since the fork diverged: 42
   upstream commits touched the same files the fork had changed, 24 of them in
   the app's views, and the workflow stops at a conflict on purpose. The merge
   was done by hand: the fork keeps its own side where the two changed the
   same behaviour (the instance context menu with Move to group, the settings
   search that highlights a row, the delete flow for bundle-managed mods, the
   world snapshot and backup tools, the quick-play launch, the fork's own
   offline accounts), and both sides are kept where they only added to the
   same list. Upstream brings importing a modpack into an existing cluster,
   importing from and exporting to other launchers, a graphics backend switch,
   a cluster reset button, a warning before a bundled mod is downloaded, the
   deleted tab in the package manager, an open-log button and a settings
   reorganization. The .sqlx metadata came with it and the merged checked
   queries still match it (every file's name is the hash of its own query).

   The fork's own work rode along: 2.30.0 shipped Performance Mode (the JVM
   is told how long a frame may wait, the repeated strings are stored once,
   the low-spec mode hands the game a heap the machine can afford and the
   video settings are written into the game's own options.txt before every
   launch), 2.31.0 shipped the performance set (the five mods that raise the
   frame rate the most, with one button for all the missing ones) and the
   per-instance performance mode, and a saved server can now be given a name.

   LESSON: a merge is not a merge until both sides' callers still find what
   they call - taking the fork's side of a conflict silently drops the
   upstream fields the upstream code constructs, and the compiler only says
   so much later. Resolve a conflict by what the other side of the tree
   *uses*, not by which hunk looks older. And a scripted "union" of two
   import blocks is a trap: it happily interleaves the two `use` statements
   into something that does not parse, so run rustfmt over every file the
   merge touched - it is the only parser on this machine.

## 2026-10-21 - The launcher says when the game asks for too much memory
   On a small laptop the stutter is usually the system paging, not the game:
   once the game takes more memory than the machine can give, the pages come
   off the disk and the frames stop. The user cannot see that, so the first
   launch of a session now says how much memory this machine can afford the
   game before the system starts swapping, and the Performance Mode page
   repeats it under the mode. The hint is said once, not on every launch, and
   it stays quiet for an instance that carries mods - a pack that needs four
   gigabytes is not the one that needs the warning.

## 2026-10-21 - options.txt belongs to the launcher, and the real cause of a bad frame rate
   The other session (Laptop, working on the PolyPlus mod in AethelOnePLUS) and
   this one agree on the rule that ends the double write: **options.txt
   belongs to the launcher**. The Performance Mode writes the video settings
   into the game's own options file before the launch and never through the
   running game, and from PolyPlus 1.3.11 the mod's low-end mode and its frame
   rate cap live in memory only - the mod stopped calling options.save() so
   it can no longer write the launcher's values back to disk. The mod side of
   this is in AethelOnePLUS/AI_HANDOFF/AUDIT.txt, the launcher side stays
   here.

   Polydium was researched for the launcher's performance set and is **not**
   going in it: PolyPlus bundles it inside its jar, Modrinth does not carry
   it (the search returns nothing, the project answers 404) and CurseForge
   only has the standalone build, which is not the patched one. The set keeps
   Sodium, Lithium, ImmediatelyFast, FerriteCore and Entity Culling; the
   patched PolyPlus jar from the mirror already carries Polydium, and the
   launcher now updates PolyPlus from that mirror.

   The mod's performance report names the cause a launcher cannot see: a
   renderer that draws on the processor (llvmpipe, lavapipe, SwiftShader,
   the Microsoft Basic Render Driver), an uncapped frame rate and the Vulkan
   backend - Polydium switches the game to Vulkan by itself when it sees a
   discrete card, and a broken Vulkan driver is a two-frames-per-second
   machine. On a small laptop with no real driver that is worth more than
   every setting in this file, and no launcher setting can fix it.

   LESSON: when two writers own one file, the fix is not to make the second
   one careful - it is to name the owner. And a "performance" complaint is
   often not a setting at all: the machine may be drawing the game on the
   processor, and no amount of tuning moves that.
